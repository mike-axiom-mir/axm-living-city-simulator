# Project Provenance and Collaboration v0.7.0

## Provenance roots

A project must refer to real state rather than inventing authority.

### Object target

The record stores:

- object ID;
- catalogue identity;
- label;
- property or storage location at creation;
- owner at creation;
- provenance statement.

The object keeps its original ID through restoration.

### Place target

The record stores the existing place ID and name. Referencing a place grants no ownership, tenancy, edit authority, construction permission, or institutional control.

### Meaning

The owner’s stated reason is retained independently from money, efficiency, skill gain, or completion status.

### History

Project history records creation, chapters, pauses, resumes, reshapes, invitations, answers, completion, release, archive, and QA setup where relevant.

## Collaboration boundary

A collaboration invitation is allowed only when the player and resident have an active community connection.

Sending an invitation:

- creates a pending request;
- creates no consent;
- creates no collaborator ID yet;
- creates no ownership change;
- spends no project resources by itself.

The resident answers later through a deterministic score and roll grounded in connection and project fit.

### Accepted

Acceptance adds the resident to bounded project participation. Later shared chapters may strengthen a creative-partner connection and record collaborator hours.

Acceptance does not create:

- co-ownership of the target object;
- authority to sell or move the target;
- tenancy or storage rights;
- home-edit or construction rights;
- household or family membership;
- employment or business authority;
- control over either person.

### Declined

Decline remains visible history. It applies no hidden relationship penalty.

## Migration integrity

Migration adds no past project, chapter, collaborator, invitation, achievement, or object intervention. New records begin only after v0.7 actions actually occur.
